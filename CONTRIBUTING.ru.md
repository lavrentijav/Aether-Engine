# Как внести вклад в Aether Engine

> **На других языках:** [English 🇬🇧](CONTRIBUTING.md)

---

Спасибо за интерес к Aether! Проект на стадии **ранней альфы**: воркспейс собирается и
проходит тесты, Фаза 0 завершена, приземлились несколько подсистем Фазы 1. Самые ценные
вклады сейчас — игровые подсистемы и закалка, описанные в [Роадмапе](docs/ROADMAP.ru.md).

### Перед началом
1. Прочитайте [README](README.ru.md), [Роадмап](docs/ROADMAP.ru.md) и [Статус](docs/STATUS.ru.md).
2. Загляните в [Известные проблемы](docs/KNOWN_ISSUES.ru.md) — часть «багов» это **допустимые отклонения Фазы 1**, а не дефекты.
3. Перед крупными изменениями заведите (или прокомментируйте) issue на GitHub, чтобы не дублировать усилия.

### Принципы разработки (не обсуждаются)
Они идут прямо из спецификации и делают Aether тем, что он есть:
- **Data-Oriented Design.** Предпочитайте Structure-of-Arrays графам OOP-объектов.
- **Cache-locality first.** Держите данные последовательно; избегайте pointer chasing.
- **SIMD-first.** Любой горячий путь вычислений нуждается в scalar-фолбэке **и** векторизованных ветках SSE4.2/AVX2/AVX-512 с выбором через runtime-диспетчеризацию.
- **Никаких глобальных блокировок.** Тяжёлая работа уходит в work-stealing пул и сливается в детерминированных Safe Points.
- **Детерминизм.** Параллельные результаты должны сливаться одинаково при каждом запуске.

### Ядро или плагин?
Ядро — для того, что нужно любому серверу и должно быть быстрым: модель мира, хранение и журнал,
генерация, физика, тик, ванильные механики, редстоун, свет, протокол и слой совместимости.
**Возможности, которые для сервера необязательны, не пишутся в ядре**; они пишутся плагинами на
API плагинов ([`docs/design/plugins.md`](docs/design/plugins.md)). Плагинов два уровня:

- **Нативный плагин** — Rust-крейт в этом workspace под `plugins/<name>/`, подключённый
  **в процессе** (in-process) на том же API/событиях, что и WASM-плагин, но **без границы и на
  полной скорости**. Для необязательных, но **чувствительных к скорости или глубоко
  интегрированных** с данными движка возможностей: хранилище прав + `/lp`, модель и проверки
  регионов/клеймов, WorldEdit, команды истории (`/co`, `/restore`), профайлер, модерация,
  essentials-teleport/player/inv.
- **WASM-плагин** — компонент в песочнице (Wasmtime), в стиле недоверенного стороннего кода, для
  необязательных и **не** критичных по скорости возможностей: экономика, магазины, форматирование
  чата, соцсети, развлечения, интеграции, статистика.

Как решать:
- *Будет ли ванильный по духу сервер работать без этого?* Да → плагин (нативный или WASM по
  следующему правилу).
- *Необязательно, но чувствительно к скорости или глубоко интегрировано?* → **нативный плагин**.
- *Необязательно, некритично по скорости и безопасно в песочнице?* → **WASM-плагин**.
- *Это на горячем пути тика (на каждый блок, сущность, пакет) или нужно каждому серверу?* →
  ядро, **без политики**: ядро вызывает фиксированный хук, а решение живёт в плагине. Механизм,
  который оператор захочет менять, — это политика, а политика никогда не в ядре.
- *Плагину не хватает данных из API?* Расширяем API (новое событие, реестр или импорт хоста, с
  версией и проверкой через `supports()`), а не переносим возможность в ядро.
- Ядро должно собираться и работать, когда **все** плагины выключены. Уже существующие
  необязательные встроенные части (экономика, `/stash`, награды) переезжают в плагины; в ядре
  остаётся только интерфейс сервиса, который они реализуют.

### Рабочий процесс
1. Форкните и создайте ветку от дефолтной: `git checkout -b feature/short-description`.
2. Держите изменения сфокусированными; одно логическое изменение на pull request.
3. Прогоните локальные проверки перед push (см. ниже).
4. Открывайте **draft** pull request рано; опишите *что* и *почему*, привяжите issue.
5. Обновляйте соответствующие документы (`docs/STATUS.md`, `docs/ROADMAP.md`), когда функция готова или план меняется.

### Локальные проверки
Тулчейн закреплён в [`rust-toolchain.toml`](rust-toolchain.toml) (Rust **1.99.0**
с `rustfmt` и `clippy`), поэтому `rustup` сам берёт нужную версию и компоненты.

```bash
cargo fmt --all -- --check                        # форматирование
cargo clippy --workspace --all-targets -- -D warnings   # линты (предупреждения = ошибки)
cargo test --workspace                            # корректность
cargo test --workspace --no-default-features      # сборка без default-фич
cargo deny check                                  # лицензии, advisories, баны, источники
cargo bench -p aether-core                        # производительность (без регрессий против QA-гейтов)
```
`cargo deny check` читает [`deny.toml`](deny.toml); CI гоняет его на каждый push
и PR через `cargo-deny-action`. Если команды нет локально — `cargo install cargo-deny`.

PR, влияющие на производительность, должны включать захват Tracy или соответствующий результат бенчмарка. QA-гейты (редстоун/сущности/взрыв/миграция) — в [README](README.md#benchmark-targets-qa-gates).

### Стиль коммитов и PR
- Ясные императивные заголовки коммитов (например, `physics: add SIMD broad-phase mask check`).
- Ссылайтесь на issue (`Closes #123`).
- CI должен быть зелёным; **не** отключайте падающую проверку ради merge.

### Замечание по CI для мейнтейнеров
После успешной сборки **не нужно повторно опрашивать pull request на каждом запуске** —
зелёная сборка это достаточный сигнал. (См. `CLAUDE.md`.)
