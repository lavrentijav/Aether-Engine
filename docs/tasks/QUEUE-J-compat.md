# Queue J — version compatibility layer (blocks + items) and follow-ups

Read `docs/tasks/COMMON.md` first. Worktree `/srv/dev/projects/Aether-Engine-wt/QJ`, branch `oc/QJ`.
Tasks in order; one commit per task (`J1: ...`). If a task is blocked, note it in
`docs/tasks/QJ-notes.md` and go on.

## Why

The engine's world is 1.21.11 (blocks: `BlockStateId`, items: `ItemTypeId`). Clients on other
versions must see *something sensible* for every block and item, and their actions must act on the
*real* item on the server. Today:

- Old codecs (`crates/aether-server/src/protocol/v755` … `v773`, `v47`) map only ~10 blocks; every
  other block becomes stone (`v767/mod.rs::block_state`, "substitution: anything unexpressible
  becomes solid stone").
- `protocol/modern/play.rs::write_stack` writes an **empty slot** when the version lacks the item
  (`v.wire_item(..) == None`), so the player sees the item vanish.
- The modern codec (1.21.11, 26.1–26.3) already has per-version tables keyed by name
  (`protocol/modern/version.rs`: `wire_item`, `engine_item`; generated by `tools/gen/versions.py`).
  Use that design as the model.

Goal: one **compat layer** — data-driven, shared by every codec — that downgrades blocks and items
the client's version lacks to the closest thing it has, and maps everything the client sends back to
the real engine object. A substitute is a disguise: it changes only what the client sees.

## J1 — block-state tables for the old codecs

- Generate per-version block-state tables (name + properties → state id) for each old protocol from
  PrismarineJS `minecraft-data` (`pc/<version>/blocks.json`), same approach as the modern tables.
  One generated file per version (or one shared table + per-version ids if that is much smaller —
  measure; keep binary size sane, and prefer a compact sorted-array format).
- Replace every hand-written `block_state()` in the old codecs with a lookup: engine state → name +
  properties → version state; a missing property takes the version's default for that block.
- Test: for every engine state whose block exists in version V, the round trip
  name/properties → V id → name/properties is identical (properties V lacks excepted).

## J2 — block substitution rules

- `tools/gen/compat/blocks.toml` (or `.json`): for a block missing in an older version, its
  stand-in, e.g. `pale_oak_* → oak_*` (same shape/properties), `copper_bulb → copper_block`,
  `crafter → dispenser`, `*_copper_* → copper / cut_copper variants`, `trial_spawner → spawner`,
  `heavy_core → iron_block`, `cherry_* → birch_*`, `mud_bricks → bricks`, deepslate ores → stone ores
  (1.16 and older), etc. Rules may chain (`newer → newer-stand-in → older-stand-in`) and are resolved
  at build time per version, so lookup at run time is one array read.
- Prefer a stand-in with the **same collision shape and properties** (slab → slab, stairs → stairs,
  fence → fence) so movement prediction on the client matches the server. Last resort only: stone.
- Test: every engine block resolves to a real block state in every supported version (no panics, no
  stone fallback for any block with a rule); a list of blocks that still fall back to stone is
  printed by a test and written into `docs/KNOWN_ISSUES.md`.

## J3 — item tables and item substitution (lossless)

- Per-version item tables for the old codecs, as for blocks (from `items.json`).
- `tools/gen/compat/items.toml`: item stand-ins, e.g. block items follow the J2 block rules; `mace →
  iron_axe`, `wind_charge → snowball`, `breeze_rod → blaze_rod`, `*_bundle → bundle / leather`,
  spears → see J4.
- The client sees the stand-in with the **real name**: set the display name (custom_name / display
  NBT for the version's slot format) to the real item's English name and add one lore line
  `Aether: minecraft:<real_id>` so it can be told apart.
- **Lossless round trip**: whatever the client sends back (window clicks, creative inventory, pick
  block, drop) must resolve to the real engine stack, never to the stand-in. Keep the authoritative
  stack on the server (the server-side windows already are); when a client packet carries an item,
  match it to the server's slot instead of trusting the id. A creative client must not be able to
  turn a spear into a real trident by moving it around. Write tests for exactly that.
- Replace the empty-slot fallback in `write_stack` (modern codec too: e.g. a 26.x-only item shown to
  a 1.21.11 client, and the reverse).

## J4 — behaviour-preserving stand-ins (spear as the reference case)

The 1.21.11 spears (`minecraft:*_spear`) have two actions: **left click = jab** (melee), **hold right
click = charge** (lunge/kinetic attack). A client without spears must still be able to do both.

- Stand-in: `trident` where it exists (1.13+; it already has a hold-right-click charge animation and
  a left-click attack), `*_sword` on 1.8.9 (right click = block animation).
- Server side: the **real** item decides the action. A `use_item` / release-use from a client holding
  the stand-in runs the **spear's** charge logic, not a trident throw; a swing/attack runs the spear's
  jab damage and cooldown. Never spawn a thrown trident entity for a spear.
- Client side: the client predicts a trident throw on release — after handling the release, resend
  the slot (and cancel any predicted projectile/animation the client started) so the spear stays in
  hand. Send the right arm animation / sound for the real action where the version has a packet for
  it.
- Generalise: `compat::Behaviour` — a stand-in can declare "client input X maps to real action Y",
  so later items (mace → axe swing with mace smash, wind charge → snowball throw spawning a wind
  charge) plug in without new special cases. Implement mace and wind charge as the second and third
  users if time allows.
- Tests: decode a 1.21.1 (v767) use-item + release sequence on a stand-in trident in a slot holding a
  real spear → spear charge event, no trident entity, slot resent.

## J5 — the older codecs and gameplay

`docs/KNOWN_ISSUES.md` item 10 says every codec older than 1.21.11 ignores the gameplay events
(no mobs, no server-side windows). The compat layer is only half useful until they do. Assess how
much of the modern codec's gameplay path the 1.20.5–1.21.x codecs (v766–v773) can share — most
packets are the same with different ids. If it is a matter of id tables and a few layout
differences, route those versions through the gameplay path; if it is large, write the plan and the
blocking differences into `docs/tasks/QJ-notes.md` and do only v767 (1.21/1.21.1).

## Extra tasks (after J1–J5)

- **J6 — durable block ticks.** The scheduler from queue C (`game/scheduler.rs`, `game/blockticks*`)
  keeps its queues in memory, so a restart drops pending falls/growth (Known Deviations, "Scheduled
  block ticks"). Persist them per chunk in the KV store alongside the chunk (vanilla keeps
  `block_ticks`/`fluid_ticks` in the chunk NBT) and reload on chunk load; fluids too if they use the
  same queue. Test: schedule, save, reload world, tick → the update happens.
- **J7 — 1.20.2–1.20.4 (protocols 764–765).** Known Issues item 13: they are kicked because their
  registry NBT blob was never written. Add the codec(s) using the 1.20.1 (763) blob as the base and
  the 1.20.2 changes (configuration phase, new chunk-batch packets). Verify with the protocol tests
  the other codecs have.
- **J8 — container blocks without inventories.** Hoppers, droppers and dispensers have no inventory
  (Known Issues item 10). Give them the same container model as chests/furnaces (`game/containers.rs`),
  windows and persistence; hopper transfer (8-tick cooldown, pull from above, push to facing) on the
  block-tick scheduler. Dispenser behaviours beyond "drop the item" may stay out; note them.
