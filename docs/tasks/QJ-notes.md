# Queue J — notes (oc/QJ)

## Scope after the split

The queue was split across agents. **This branch (oc/QJ) owns only J1, J2 and
J5** — block tables, block substitution, and the older-codec/gameplay
assessment. J3 + J4 (item tables/substitution and the spear stand-in) were
removed from this branch and moved to the items agent (oc/KQ/oc/QK); J6, J7 and
J8 go to three other agents. Do not expect item code here.

## J1 + J2 — done

* Per-release block-state tables for every flattened codec (protocols 755–773),
  generated by `tools/gen/compat/gen.js` from PrismarineJS `minecraft-data`,
  looked up through `protocol::compat::blocks::BlockTable`. 1.8.9 (47) keeps the
  pre-flattening model via `LegacyTable` / `V1_8`.
* Substitution rules in `tools/gen/compat/blocks.json`, resolved at generation
  time and chained. **Every engine block resolves to a real state on
  1.17–1.21.10** (zero stone fallbacks). 1.8.9, which has 198 blocks against the
  engine's 1,166 and no metadata table, still falls back to stone for 422
  blocks; the list is `STONE_FALLBACKS` in `gen::v1_8` and is recorded in
  `docs/KNOWN_ISSUES.md` A.14.
* The API was extracted into a small, documented `compat/blocks.rs`
  (`BlockTable::state`, `LegacyTable::vanilla`/`engine`, the per-release
  statics, and `compat::block_table`/`state_for` by protocol id) so the item
  layer can reuse the block rules for block items: it should read the same
  `tools/gen/compat/blocks.json` and the same `resolver` helper in `gen.js`.

## J5 — older codecs and gameplay: assessment, plan, blockers

### What "the gameplay path" is

`ProtocolCodec::full_gameplay()` plus the neutral event sets. A codec that
returns `true` gets the server-side survival game: entities, combat, health,
hunger, windows, effects. The modern codec (`modern/mod.rs` + `modern/play.rs`)
implements it; every codec from v755 to v773 returns the default `false` and
keeps the old client-trusting subset, so 1.20.5–1.21.10 clients get no mobs,
no server-side windows and no survival (KNOWN_ISSUES item 10).

### How much can be shared

The wire formats across the v766–v773 span are close to 1.21.11's:

* configuration phase with **per-registry packets** since 1.20.5 (766), same
  shape as 774;
* paletted chunk containers and the combined chunk+light packet;
* item stacks are `count, id, added-components, removed-components` since
  1.20.5, so `write_item` is the same shape;
* entity metadata is `(index, serializer, value)…0xFF` the same way;
* the packet **ids** differ, and a handful of **layouts** do (chunk section
  fluid count from 1.21.2, `entity_position_sync` from 1.21.2, the login
  packet's `sea_level` from 1.21.2, damage-type/biome registry details).

So the packet *set* is not the blocker. The blocker is that those codecs never
produce or consume the gameplay `ClientEvent`/`ServerEvent` variants at all,
and each one would need them written out.

### Concrete gap for v767 (protocol 767, 1.21/1.21.1)

`v767/mod.rs` currently encodes 13 event kinds (`KeepAlive`, `ChunkColumn`,
`UnloadColumn`, `TabListAdd/Remove`, `SpawnPlayer`, `EntityMove`,
`DespawnEntity`, `BlockChange`, `AckBlockChange`, `SetCenterChunk`,
`CommandTree`, `Chat`) and decodes movement, dig, place and chat. To be
`full_gameplay` it also needs:

* **encode**: `SpawnEntity`, `EntityMeta`, `EntityPos`, `EntityHead`,
  `EntityVelocity`, `EntityAnimation`, `EntityStatus`, `Damage`, `Collect`,
  `Equipment`, `UpdateMobEffect`, `RemoveMobEffect`, `UpdateAttributes`,
  `Health`, `Experience`, `Time`, `WindowContents`, `OpenWindow`,
  `CloseWindow`, `WindowProperty`, `WorldEvent`, `BreakAnimation`, `Respawn`,
  `GameModeChange`, `SetHeldSlot`, `Teleport`, `DeathMessage`, `Explosion`,
  `Sound`, `MoveEntity`, `DropItem`, `OpenContainer` — about 30 arms, each a
  1.21.1 packet layout;
* **decode**: `HeldSlot`, `CreativeSlot`, `UseItem`, `Swing`, `Interact`,
  `StartDig`/`CancelDig`, `DropHeld`, `SwapHands`, `Input`, `PickBlock`,
  `WindowClick`, `ContainerClose`, `ChangeGameMode`, `Respawn` — about 14
  arms;
* **join**: `initial_hotbar`, `set_held_slot`, `set_health`, player abilities
  and the inventory resync — the v767 `finish_join` currently sends only
  position;
* `supports_containers`, `full_gameplay`, `block_for_item`.

The per-packet ids and layouts are available from `minecraft-data`
`pc/1.21.1/protocol.json` (the same source this codec already uses), and the
slot format matches 1.21.11's. This is roughly 500 lines, mostly mechanical.

### Why v767 was not implemented here

1. **Reusing the modern codec is not a small change.** The obvious move — give
   `modern::Codec` a `Version` for 1.21.1 — fails on two points: `Gen::V1_21_11`
   is 1.21.11's *layout*, not 1.21.1's (the login packet's `sea_level` from
   1.21.2 and `entity_position_sync` are 1.21.2 changes that would be wrong on
   1.21.1), so a new `Gen` variant and its branches are needed; and the modern
   login path builds the *1.21.11* registries (`registry::registries()`), while
   v767 carries its own `registry.rs`. Generalising both touches the
   1.21.11/26.x path that other work depends on — too risky for a queue that
   cannot test against a client.
2. **A hand-port into `v767/mod.rs` cannot be verified here.** There is no live
   1.21.1 client and no `versions/1.21.1` reports on this machine. The existing
   v767 codec is itself "not verified against a live client", so a blind
   ~500-line port would ship unexercised gameplay for an untested version — the
   exact combination the queue's J4 test was meant to catch and cannot.

The plan is therefore recorded rather than executed. If the project wants a
first gameplay-capable old codec, the lower-risk route is to add the layout
branches for 1.21.1 to the modern codec (a `Gen::V1_21_1`) and drive v767
through `modern::Codec`, so the gameplay encode/decode exists in exactly one
place; that is a refactor of `modern/`, not of `v767/`.
