### A. Current known problems (early alpha)
1. **Gameplay runs on 1.21.11 and 26.1–26.3 only; engine-level subsystems are still unbuilt.** The server now has a survival game layer (`crates/aether-server/src/game`: mobs, items, combat, hunger, crafting, chests, furnaces — see item 10), but it is a server-side layer, not the ECS/Flow-Field design of the roadmap; redstone and the full staged physics pipeline are not implemented. **A standalone, tested redstone core now exists** (`crates/aether-redstone`): weak/strong power; wire, repeater, comparator, observer, redstone torch and wall torch, lever, button, block of redstone, lamp, daylight detector, pressure plates (wood/stone and weighted), tripwire and hook, and the target block. Each is a `BlockBehaviour` reached through a `BlockStateId`-indexed table (no string comparisons, no core edits to add a component — `connects_to_wire` lets a new block decide its own wire connection), all logic over a `RedstoneView` with an in-memory `MemWorld` for tests. State changes go through `set_block(pos, state, flags)` with vanilla's `Block.UpdateFlags`; neighbour updates run through a port of `CollectingNeighborUpdater` (depth-first LIFO, multi-neighbour updates yielding to fresh ones, chain limit); the redstone-torch burnout log is per world on the `RedstoneView`; support predicates are vanilla's slice-based `SupportType.FULL/CENTER/RIGID`; and wire/repeater/torch/lever/button pop off when their support is removed. The comparator reads container fill level, the daylight detector reads the sun, pressure plates read entity counts, and the target block reads projectile hits — all through `RedstoneView` host hooks, since the crate has no item/entity/environment model. It is deliberately **not wired to the server tick loop** — the game hook is a later stage — and it is the simple vanilla-style update model, not the compiled dependency graph. Known differences from vanilla 1.21.11 at this stage: a block's **support** shape uses the collision shape where vanilla has a separate `getBlockSupportShape` (no observable circuit difference for the ~9 overriding blocks); a component the engine destroys is reported through `RedstoneView::drop_block` rather than spawning an item itself; the daylight detector's `SupportType.CENTER`-style predicates for redstone are exact but the sky/sun and entity inputs are host-supplied; and pistons, quasi-connectivity, hoppers (as components), droppers/dispensers, doors, rails, note block and TNT priming are absent.
2. **SIMD parity only partially validated.** `Scalar / SSE4.2 / AVX2` paths are implemented and unit-tested; `AVX-512` is *detected* but routed to the AVX2 path — there is no native AVX-512 backend yet.
3. **Determinism unproven.** Parallel subsystems must merge at Safe Points; the merge points are specified but not validated, and the work-stealing scheduler that would exercise them does not exist yet.
4. **Experimental 1.8.9 server is unverified against a live client.** `aether-server` speaks protocol 47 in offline mode with no compression/encryption, and its framing is checked only against a raw socket client. A real Minecraft 1.8.9 client may still reject some packets (chunk-data format is the most likely gap). It binds to loopback by default and must not be exposed publicly.
5. ~~**Players are visible but not tab-listed.**~~ **Fixed:** the Player List Item packet (0x38, protocol 47) now goes out on join and leave — action 0 adds an entry with the player's **binary** UUID (16 raw bytes, the same form Spawn Player uses; only Login Success is the hyphenated string), name, an empty GameProfile property list (offline mode has no skin signature to send) and a synthetic game mode/ping; action 4 removes it. Each add is emitted *before* the corresponding Spawn Player, because a 1.8 client drops a spawn for a UUID it has no tab entry for. With no properties a client shows the default Steve/Alex skin, which is the correct result for offline mode. The exact byte layout is pinned by a unit test.

6. **Block states work, except where they depend on a neighbour.** `BlockStateId` is now the vanilla flattened block-state id (29,671 states over 1,166 blocks — see [DESIGN_NOTES §9](DESIGN_NOTES.md)), and placement chooses a state from the player's yaw and pitch, the clicked face and the cursor. Re-measured against a live 1.21.11 client (`tools/probe/states3.js`):

   | placed | before | now |
   |---|---|---|
   | `oak_stairs`, looking N/E/S/W | `facing=north` in all four | follows the look direction |
   | `oak_slab` on a top face | `type=bottom` | `type=bottom` |
   | `oak_slab` on a **bottom** face | `type=bottom` | `type=top` |
   | `oak_door` | `half=lower` only, air above | two blocks, `lower` + `upper`, facing agrees |
   | placed into water | `waterlogged=false` | `waterlogged=true` |
   | two adjacent `oak_fence` | no connections | connect, in either build order |

   **Neighbour-dependent shapes settle both ways now.** A block-update pass (`placement::neighbour_updates`) re-runs when a neighbour changes, so a fence built *away* from an existing one connects instead of keeping the unconnected shape it was born with. It covers fences, walls, panes/bars and stair corners — the families whose shape is a pure function of the six touching cells.

   what is left is the class of property that needs a wider propagation than a single reshape: redstone wire shape; a door's hinge side; grass turning `snowy`. A fence placed today is a correct, connected fence.

   **Interaction now beats placement.** Clicking a door, trapdoor or fence gate toggles it instead of building against it — the reported "door opens and instantly shuts with a block in front of it" was the server placing a block where the client had predicted an opening, and the ack then reverting the prediction. Both halves of a door toggle together. Sneaking still builds against it, or a door could never be placed beside another. Detected from the block's own data — anything declaring an `open` property — so there is no list to maintain.

   **Stairs take their corner shape**, transcribed from `StairBlock`'s bytecode in the 1.21.11 server rather than from memory: the four corner cases differ only in which of `left` and `right` they name. Computed at placement, and re-computed by the neighbour-update pass when a neighbour changes — both places vanilla computes it.

   **Open question, measured but not explained:** a headless client's *view* of a toggled door trails the server by a click or two, while the server's own state is right every time and nothing is placed in front. It may be the client's prediction handling rather than ours — mineflayer's differs from the game's — so this wants checking with a real client before it is chased.

   Three smaller gaps inside the part that does work:
   - **Attachment-based facing is not distinguished from look-based facing.** A ladder or a wall torch takes its direction from the surface it is on; nothing in the block's own data says so, and they get the look-based answer.
   - **Anvils are 90 degrees out.** `AnvilBlock` uses `getClockWise()`, a third rule that is not implemented.
   - **Properties do not vary within a block, except collision.** An unlit redstone lamp still emits nothing, a double slab is not a full opaque cube, an open trapdoor still occludes light as its closed form. `minecraft-data` publishes light and occlusion per *block*, not per state, so `STATE_PROPS` stays uniform within a block; closing the light half means asking the game itself, which is the technique the worldgen work uses. **Collision is now the exception**: the boxes come per state from `blockCollisionShapes` (see the next item), so an open door or gate no longer collides, a top slab sits in the upper half and a fence is 1.5 tall.

   **Placement now enforces attachment and support.** `placement::rules` holds the authoritative `#minecraft:replaceable` list — generated from the pack into `placement/data.rs` by `tools/gen/placement.js`, with the compiled-in copy as the no-pack fallback and the startup log naming which was used — and the "what can be placed on what" support table with its reverse index, rendered to [`BLOCK_PLACEMENT.md`](BLOCK_PLACEMENT.md) (+`.ru.md`). Every placement is checked before anything is written, so the reported bugs are closed: grass (and the other plants) on the wrong soil, and `leaf_litter` on a wall or under water, are refused. The block *sets* (dirt, sand, dry vegetation, bamboo, big dripleaf, jungle logs, snow, …) are the pack tags; the rule *shapes* are ported from vanilla's classes (`VegetationBlock`, `LeafLitterBlock`, `BaseTorchBlock`, `WallTorchBlock`, `LadderBlock`, `MultifaceBlock`, `SeagrassBlock`/`KelpBlock`/`SeaPickleBlock`, `SmallDripleafBlock`, `CactusBlock`, `SugarCaneBlock`, …). Two rules go **beyond** vanilla 1.21.11 and are marked *curated* rather than claimed as ports: `leaf_litter`'s "never under water" half (vanilla's `LeafLitterBlock.canSurvive` only checks a sturdy face below — the water trigger is the owner's, our addition), and accepting a torch clicked on a wall against that wall (vanilla would place a `wall_torch`, which this engine cannot turn an item into). Remaining approximations inside this: a support face is read from the block's **collision** shape where vanilla keeps a separate `getBlockSupportShape`, so a torch on a *fence post* — which vanilla allows through `SupportType.CENTER` — is refused here; the item→wall-torch conversion is not modelled, so a torch clicked on a wall is accepted against that wall but rendered standing; hanging lanterns and wall-hanging signs are not distinguished from their standing/ceiling forms; sea grass/tall sea grass exclude magma and kelp does not (so kelp on magma is refused too, the conservative direction); and a refused placement is acked but otherwise silent, with no client message.


7. ~~**The 1.17 / 1.17.1 chunk encoding is rejected by a real client.**~~ **Fixed:** the section encoder wrote 1.18's *single-valued* palette (`bits per entry = 0`) whenever a section held one repeated block, which the old code also used for every empty section. 1.17 predates that form (it first appears in `PaletteType1_18`), so a client read the palette value as a length, consumed the wrong number of bytes and ran off the buffer — surfacing as `Attempted to read beyond the bounds of the managed data` while reading the next section's block count. Sections are now encoded exactly as 1.17 requires: a big-endian non-air count followed by a **4-bit indirect** palette, and an all-air section is **omitted from the section bitmask** entirely, which is also what the vanilla server does — it never sends an empty section. Byte-level tests pin one section and an empty column; both 1.17 and 1.17.1 are covered.

8. **Vanilla worldgen: decoration is vanilla-like, not exact; some features and most structures are missing (only the igloo is placed).** Terrain shape, biomes, surface rules (now including `temperature`, `steep`, `hole` and badlands banding) and carvers are matched stage by stage against the game's own generator. The decoration step runs the pack's placed features with the game's seeds and order, and lands 99.7% of all blocks and 96.7% of top blocks against a vanilla server world — but it is not position-exact: vanilla's result depends on which neighbouring chunks were decorated first, and trees, ores and plants overlapping a chunk border settle differently. Leaf `distance` values differ in a few percent of leaves. Not generated at all: structures (villages, mineshafts, strongholds…), sculk, root systems. Desert wells, dungeons (`monster_room`), geodes, fossils, pointed dripstone and multiface spreading (glow lichen) are ported. `minecraft:cinnabar` and `minecraft:sulfur` are not in this engine's block registry, so those surface leaves fall through rather than placing a substitute.

   **Biomes are sent on 1.21.11:** the codec registers all 65 biomes (temperature and precipitation from `minecraft-data`, rainfall and water colours by family, vanilla's sky-colour formula) and writes each section's 64 entries as a paletted container; the other codecs and the noise generator still show plains. The block containers also widen past four bits — a decorated section with more than sixteen states used to corrupt the column.

   **Throughput is no longer the problem.** It was: the generator once managed 35 columns in 120 s against a live client, about 10 s a column. Two bugs in the density graph's node cache did it — the `cache_once` / `cache_2d` / `flat_cache` markers were no-ops that memoized nothing, and the cell-corner cache packed `x0`/`y0`/`z0` into overlapping bit ranges, so with `min_y = -64` it collided on nearly every lookup. A third fix sized the corner cache to the real working set. Measured against a real 1.21.11 client at view radius 8: **spawn at 1.87 s, all 289 columns in ~21 s** cold, and within the first five seconds once the column cache is warm.

9. **No headless-client regression suite yet.** `tools/probe` connects a real 1.21.11 client (mineflayer) and reports what the server actually sends; it found two live defects in one run — a seven-entry item→block table that placed every other block as **stone**, and a missing `set_health` that stalled every bot client before spawn. It is a set of scripts, not a test suite, and nothing runs it automatically. For 26.x, `tools/wire` goes further: a client compiled against the release's own server jar decodes every packet with the game's codecs and builds the registries as the client does. On its first runs it found two defects mineflayer cannot see: 26.3's byte-array `BitSet` (every chunk's light masks misread) and cave/void air counted as blocks in each section's non-air count. It needs the release's jar and Java 25, so CI does not run it either.

10. **What the survival layer does not do yet** (1.21.11 and 26.1–26.3 run it natively; protocols 764–773 — 1.20.2 through 1.21.10 — now route through the same gameplay path: entities, combat, health, hunger, windows and effects, via `modern::play` driven by each release's packet ids and the compat block/item tables. Protocols 1.8.9–1.20.1 (≤763) keep the client-trusting subset — no mobs, no server-side windows):
    - **The 1.20.2–1.21.10 path shares 1.21.11's layout where it is identical and gates the rest by release, but a few per-release registries cannot be exact.** 1.20.2–1.20.4 additionally use the pre-1.20.5 forms, gated in `modern::play`: the NBT `Slot` (a presence flag, id, `i8` count and optional NBT, not the two data-component lists), attributes named by identifier rather than indexed, the pose serializer at 20, the pre-`SpawnInfo` respawn packet, and — in 1.20.2 only — JSON text for system chat, window titles and death messages, which 1.20.3 turned into NBT components.
    - **A few per-release registries cannot be exact.** Entity-type, attribute and menu ids come from the release's own `minecraft-data` dump, so a point release that shares a protocol id (1.21.2/1.21.3, 1.21.7/1.21.8, 1.21.9/1.21.10) sees the later release's ids where they differ. Explosion particles are not sent: the packet was rebuilt in 1.21.9 and the older particle registry is not available here, and the event is cosmetic. The static tags packet is still not sent on these codecs, so water and `climbable` behave as they did before.
    - **Mob AI paths now, with caveats.** Ground mobs run A\* over the block grid (`aether_world::pathfind`, a simplified `WalkNodeEvaluator`): a cell is walkable when the block below can carry a mob and the cell plus the one above are clear, neighbours step up one block or drop up to three, lava/fire/cactus are refused, and step/drop decisions read the **per-state collision shapes** — so a slab is a step, a fence or wall is not, and a closed door is a wall. Each mob caches its path and re-solves it when the target drifts more than two blocks, the next waypoint becomes blocked, the path runs out, or the mob stops making progress (a block dropped onto its path); the search is charged against a node budget shared by every mob each tick, and a mob that cannot afford one steers straight, refusing exactly the drops the search would. **Still missing:** doors are not opened (a closed door is a wall), spiders do not climb, gaps wider than the max drop are not jumped, there is no swimming pathfinding, and the goal is the target's own cell rather than its reachable neighbourhood — so a mob chases towards where the player *is*, not where they can be cut off. Eight kinds exist: cow, pig, sheep, chicken, zombie, skeleton, creeper, spider. No breeding, taming, villagers or the Nether/End mobs.
    - **No redstone or fire spread.** Falling sand/gravel/concrete powder, crop growth (wheat, carrots, potatoes, beetroot, sugar cane, cactus) and leaf decay **do work** now (`game/blockticks.rs` and its submodules, driven by the scheduled queue and a vanilla-rate random-tick pass — three blocks per 16³ section per tick). The scheduler is durable now: its pending ticks are written per chunk (`game/tickstore.rs`) and reloaded as each chunk comes in, so a restart no longer drops a fall or a growth. Two deviations there: **light is treated as full-bright**, so crops grow in the dark and under a roof where vanilla's `>= 9` check would refuse; and the `DIRT`/`SAND`/`LOGS` block tags the support and distance rules read are name lists, not the real tags. Crops still cannot be bone-mealed. Water and lava **do flow** now (`game/fluids.rs`: scheduled updates with vanilla delays, levels, falls, slope-seeking, infinite water, lava + water → obsidian/cobblestone/stone). Flowing fluid pushes mobs and items with vanilla's `getFlow` vector at the `0.014` motion scale; waterlogged blocks act as contained water sources that feed and combine with neighbouring flows (but never spread on their own, as in vanilla); and freshly generated fluid that can flow is given a scheduled tick when its column loads, bounded per tick.
    - **Recipes are read from the data pack now.** `game/recipes.rs` loads `data/minecraft/recipe/*.json` and the item tags it references: in 1.21.11, **1,470 recipes** — 706 shaped (matched straight **or mirrored**, with a space in the pattern requiring an empty cell), 320 shapeless, 116 cooking (smelting 200 / blasting 100 / smoking 100 / campfire 600 ticks, each with its own experience), 254 stonecutting, 30 smithing and 32 transmutation — plus 12 dynamic `crafting_special_*` recipes (banner duplication, book/map copying, firework crafting, armour dyeing, item repair, shield decoration) that are counted and listed but not run. Ingredients may be **item tags** (`#minecraft:planks`), resolved recursively from `data/minecraft/tags/item/*.json` (including subdirectories); a consumed ingredient leaves its crafting remainder, exactly the five vanilla sets one — a bucket from a water, lava or milk bucket, a glass bottle from a honey bottle or dragon's breath. **Transmutation crafts in the ordinary grid** (bundle and shulker-box dyeing); the shaped matcher accepts a genuinely mirrored pattern; and shapeless ingredients are matched as a bipartite assignment, not greedily. The compiled-in table (`game/data.rs::SHAPED`/`SHAPELESS`, from the same source) remains the fallback for a server run without a pack, so a packless server still crafts — and a packless furnace, smoker or blast furnace all cook from the compiled smelting table. What is still missing: there is no **stonecutter, smithing-table or campfire UI**, so those recipe kinds are loaded and indexed but unreachable in play; recipe **result components** are not modelled, so the sixteen `suspicious_stew_from_*` recipes return a plain stew without its effect; and the server **sends no recipe-book packets** — a client's recipe book stays empty, which is harmless (crafting is server-authoritative and the client never offers to place a recipe). The serverbound book packets (`Place Recipe`, `Recipe Book Change Settings`, `Recipe Book Seen Recipe`) are not recognised by any codec and decode to `ClientEvent::Ignored`.
    - **No enchanting, anvils, smithing or villager trading; beds only set the spawn point and skip the night.** Status effects **do** work (`game/effects.rs`): the Update / Remove Mob Effect packets are sent on 1.21.11 and 26.1–26.3; golden apples, enchanted golden apples, poisonous potatoes, spider eyes, pufferfish, rotten flesh and suspicious stew apply them; and regeneration, poison (never below one heart), wither, hunger, absorption, resistance, fire resistance and speed/slowness (movement-speed attribute) are acted on. Effects tick, expire, cure with milk, and are saved with the player. **Brewing and potions now exist** (`game/brewing.rs`): the vanilla `PotionBrewing` table, a brewing stand with an ingredient, blaze-powder fuel and a 400-tick brew, water bottles from a water source, drinking (32 ticks, effects, glass bottle back) and thrown splash/lingering potions with distance-scaled effects and a lingering area cloud, the potion carried by the `minecraft:potion_contents` component on the wire. Three deviations remain there: the brewing stand's `has_bottle_0/1/2` block-state bits are not set, so the client does not draw the bottles on top of the block; a mob that catches a potion runs the effect in the server model but the effect is not sent to clients as entity metadata, so nothing shows on the mob; and a water splash only applies the potion's (empty) effects, it does not douse fire. Beacons and conduits still do not exist, and every effect outside the acted-on list is carried and displayed with no server-side rule.
    - **XP orbs** are entities now (`minecraft:experience_orb`): ores, mobs killed by a player and smelting drop them on the ground; they drift to a nearby player, merge up to an orb's cap, and credit whoever picks them up. Fortune/Silk Touch do not yet change the amount (enchantments are not modelled).
    - Chests **do double**: two adjacent chests merge into one 54-slot window (`type=left`/`right`), breaking one half splits the other back to single. Hoppers (5 slots), droppers and dispensers (9 slots) **now have inventories** — the same container model as chests and furnaces (windows, persistence, provenance) — and hoppers **move items**: on the block-tick scheduler, one item every eight ticks, pulling from the container above and pushing into the container they face. What is still missing: the `enabled` redstone property is ignored (a hopper is always on), a hopper does not pick up item entities or minecart entities, and a dropper/dispenser does not fire on a redstone pulse — beyond holding their items they do nothing.
    - ~~**Block collision is per cube**~~ **Fixed:** collision boxes come per block **state**, generated from `minecraft-data`'s `blockCollisionShapes` (`registry::shapes`, generator `tools/gen/collisions.js`). Slabs collide as half cells, stairs as their step shape, fences as their 1.5-tall rails, and an open door or fence gate as nothing at all; grounded entities walk (step) up a slab but not a full block. `aether-physics` resolves an AABB against the box list and a state-aware `BlockView` supplies it.
    - **Anti-cheat is minimal**: mining time is checked at half the expected duration, reach at 6 blocks; movement is trusted.
    - **Light is not consulted for spawning**: monsters spawn at night under open sky, or at any time under cover.
    - **Loot tables now drive drops, with documented gaps.** Block and mob drops come from the pack's `data/minecraft/loot_table/**.json` (`game/loot.rs`: pools, constant/uniform/binomial rolls, weighted entries, alternatives/groups/sequences, tags and nested and inline tables, the common conditions including `match_tool` with silk-touch/fortune predicates and `entity_properties` with `components`/`type_specific`, the common functions, and table-level `functions`), and fall back to the built-in tables when no pack is set. A naturally generated dungeon or igloo chest is filled on its first access (a player open, a hopper draw, or being broken — as vanilla unpacks the `LootTable` on the first `getItem`/`removeItem`/`isEmpty`), seeded from the world seed and position. Three gaps are accepted for now: (a) the generator keeps no block entity, so a generated chest's table is *inferred* from the structure around it — a nearby `spawner` means `chests/simple_dungeon`, a nearby `brewing_stand`/`water_cauldron` means `chests/igloo_chest` — rather than stored as vanilla stores the `LootTable` string; (b) functions that *write* an enchantment or component (`enchant_randomly`, `enchant_with_levels`, `set_damage`, `set_components`, `copy_components`, `set_potion`, `set_enchantments`) parse but do nothing, because enchantments are not item components yet, so an enchanted item drops as a plain one; (c) a condition or predicate the parser does not model fails closed (no drop) — including `entity_properties` predicates the engine cannot answer (`equipment`, `vehicle`, `nbt`, unknown `type_specific` ranges). Every skipped construct and every unmodelled predicate key is recorded and reported once at startup, and a `loot_table` reference cycle is cut rather than recursed. Gameplay still supplies no `silk_touch`/`fortune`/`looting` (enchanted tools are not modelled), so those predicates read zero in a live session even though the engine computes them correctly when a context carries them.

11. **The journal keeps every event forever.** Loading a column no longer replays its whole history (per-column checkpoints), but the history itself still grows without bound on disk; packed cold segments are still the plan (ROADMAP, Phase 1 "History at scale"). Bulk block edits are now grouped into one `block_group` revision each (CMD-30a, format v6), so a `//set` costs one entry rather than one per block, but other operations (a dig, a craft, a tick of fluid flow) are still per-event. Fluid flow is written without a journal entry, so in a sub-chunk rebuilt after a generator change, flowing water resets to what the generator made until something disturbs it.

12. **Item provenance still has blind spots, but the merge hop is tracked now.** Journal format **v4** records a stack topping up another as an `item_merge` that names the source uid (before, the arriving uid was destroyed and the destination's count simply grew, so the hop had no source at all), and a destroy carries a `reason` byte (consumed, despawn, crafted, creative replace, …) so a disappearance says why. A split is a mint of the new identity plus a move of the source, and `item_derive` is reserved for a real output (craft/smelt/brew) from its consumed ingredients. What remains: events are per click, not per operation, until revisions group them; the economy still journals its own moves with uids of their own beside the real ones; items in inventories from before the uid change were never minted, so their first event reads as an anomaly in `/audit`; and fights and trades between players are not recorded yet.

13. ~~**1.20.2 through 1.20.4 cannot connect.**~~ **Fixed:** protocols 764–765 are served by their own codecs (`protocol/v764` 1.20.2, `protocol/v765` 1.20.3/1.20.4), built on the 1.20.1 (763) NBT blob. Like 1.20.1 they send the whole registry set as one blob — but with an **anonymous root**, and in the **configuration phase** 1.20.2 introduced rather than inside Play Login. Columns are wrapped in 1.20.2's **chunk-batch** flow-control packets, and 1.20.3's differences are pinned in its own module (System Chat as an NBT component, the UUID on the resource-pack packet, game event 13 for "wait for chunks", and the moved `minecraft:player` entity-type id). 1.20.2 also reordered the Unload Chunk packet to Z-before-X, which its module follows. As with the 1.20.1 codec, the registry blob stays minimal (dimension type, biome, chat type). Verified by encode/decode tests only; no live client of these versions was available.


14. **Older codecs translate and substitute blocks; 1.8.9 now resolves every engine block.** Queue J's compat layer (`crates/aether-server/src/protocol/compat`, generated by `tools/gen/compat/gen.js` from `blocks.json` + PrismarineJS `minecraft-data`) maps every engine block state into each older release's own numbering by name and properties, and substitutes the closest block a version lacks — `pale_oak_*` → `oak_*`, `cherry_*` → `birch_*`, `copper_bulb` → `copper_block`, `crafter` → `dispenser`, `trial_spawner` → `spawner`, `heavy_core` → `iron_block`, `mud_bricks` → `bricks`, deepslate/copper/tuff families and so on. The rules chain, so `bush → short_grass → grass` lands on the oldest name that exists. **Every release from 1.17 through 1.21.10 resolves every engine block** (zero stone fallbacks). 1.8.9 (protocol 47) is pre-flattening: a cell is `(id << 4) | meta`, so it has only 198 blocks and a variant is told apart by its metadata. The rules carry that metadata (`metaMaps` for colour/wood/coral and a literal elsewhere), so a wool colour, a wood type, a flower species, a coral colour or a slab variant lands on the right one instead of its block's default. **1.8.9 now resolves every engine block too — `gen::v1_8::STONE_FALLBACKS` is empty**, pinned by the `one_point_eight_resolves_every_engine_block` test. What no rule covers at all (a modded engine id) still becomes stone.
15. **The item compat layer is wired into the pre-1.20.2 codecs' join/placement path, but those codecs still do not run the gameplay path.** `protocol::compat` has per-release item tables (`compat::items`) and behaviour-preserving stand-ins (`compat::behaviour`, task J4); the codecs from 1.20.2 on show an item their version lacks as a named stand-in rather than an empty slot, and the 1.8.9–1.20.1 codecs (protocols ≤763) now resolve their join hotbar, their held-item placement and an echoed stand-in through the same tables (`legacy_codec_item_hooks`, RP1). They still do not render arbitrary stacks or run the gameplay path (item 10), so their tables stay foundational until those codecs are routed through gameplay. Two further temporary gaps inside this layer:
    - **Block items follow the block rules.** A *block* item a version lacks now resolves through the same `tools/gen/compat/blocks.json` rules and the same resolver (`tools/gen/compat/gen.js`, required as a module) as the block itself, so a held icon and the block it places downgrade together. A block no rule covers takes the version's stone item, the block table's own last resort, so `ITEM_FALLBACKS` holds only items that are not blocks (the generator no longer uses the `barrier` placeholder); 1.8.9 uses the legacy-only rules (T4), so its block items follow its legacy block table, and a legacy block with no same-named item aliases to its item (`standing_sign`/`wall_sign` → `sign`, the banner blocks → `banner`, a campfire's `fire` → `flint_and_steel`). The only block items that still show stone are those whose block also has no rule (granite, deepslate, …), where the block table is stone too — so no block item whose block has a rule falls back to a generic item. Tests in `compat::items` assert no fallback names an engine block in any release and that signs, banners and campfires avoid stone.
    - **The round trip is per move, and the real-item multiset is conserved — a merge of wire look-alikes is refused.** `ItemTable::resolve_reported` handles a client echoing a stand-in back into the *same* slot; `ItemTable::resolve_change` handles the rest against the carried shadow (`Carried { item, count }`, `PlayerState::creative_carry`). Two engine items that share a wire id but are different real items (a disguised `pale_oak_planks` shown as `oak_planks`, a horse harness shown as leather) are **look-alikes**. If a click would combine them — the slot and the incoming item share a wire id but differ as real items, and the client (seeing one stackable kind) merges them — the report is **refused** (`Resolution::Reject`) and the window resynced, because honouring it would convert one real item into the other; this holds in either direction and at any stackability. An *unstackable* look-alike pair (a spear shown as a trident onto a genuine trident) cannot merge, so the client swaps them, and that swap is allowed — it takes the placed item into the slot and **shadows the displaced slot stack** so the client keeps the real item it is carrying (without that shadow a later placement of the client's spear, which it can only describe as "trident", would be written as a genuine trident). A reconciled report of the same real item (or an empty slot, or a different wire id) resolves as before: a placement, a merge of one real item, a swap, or a creation with a cursor the server does not know (`N4`); a same-wire report the shadow cannot explain is treated as a merge the slot absorbs, and the server holds **no** shadow rather than inventing one from the slot (which would fabricate). The net effect is that the server's real-item multiset changes only by an explicit creative conjure or removal — never by a merge. `session::record_slot_change` resolves each report through `compat::items::table_for(codec.protocol_id())`; on `Reject` it **resyncs the open window with the cursor set to the shadowed stack** (the server's `PlayerState::cursor` is kept equal to the shadow, so the resync shows the client the item it is really carrying rather than an empty cursor that would silently destroy it) and, on any outcome, mirrors the shadow into that cursor. A version with no table (1.21.11 and later, whose ids are the engine's own) is trusted as before. Known limits: a conjure of the *stand-in's own item* with the same count as the shadow is information-theoretically indistinguishable from a legitimate move and resolves to the engine-only item; and a partial placement of a *conjured genuine* item leaves a remainder the server cannot track (so the server may under-count the cursor, never over-count). Tests cover the slot → cursor → slot move, a swap onto a same-wire slot, a swap with an unshadowed cursor, a conjure onto a non-empty cursor, a partial placement, that both directions of a look-alike merge are refused, that an unstackable look-alike swaps *and shadows the displaced item*, and a property test over random window actions — with wire-colliding pairs (`pale_oak_planks`/`oak_planks`, a horse harness/`leather`, `iron_spear`/`trident`) seeded *and* in the conjure menu, modelling the resync's cursor as the session's `st.cursor` (the shadow) — asserting the server never loses or transmutes a real item and never invents one the client does not hold.


16. **Anti-xray is optional and off by default.** The `[anti_xray]` module has two modes. `engine` (the default) masks an ore-like block whose six neighbours are all opaque as the actual surrounding block (whichever opaque non-hidden block is most common among the six — deepslate, netherrack, andesite, …), and re-sends it for real when a neighbour changes. The hidden-block list is configurable (default: every ore, ancient debris, monster spawner). `culling` is the design in `docs/design/visibility-culling.md`: `aether_world::visibility` is the pure `16³` section face graph and reachable-set BFS (`view_distance` in sections), `crate::visibility` is the cache, per-player state, per-cell masking and reveal budget, all through the existing per-version chunk writers. Cell granularity is two-level: the cheap section BFS gives coarse visibility, then each visible section's cached cell mask (from its own face openings) decides which of its `4×4×2` cells are real — no global cell search. Both are wired into `players.rs::render`, the join burst and the game tick; server-side single writes (`/setblock`, creative, `/rollback`) are masked through the same code path. A pre-AX1 `[visibility]` table is migrated to `mode = "culling"` with a startup warning (`Config::migrate_legacy`), and the old `ray_refinement`/`mask_buried_ores` keys are accepted and reported. Its known limits:
    - **Culling's granularity is the `4×4×2` AVX-cell, not the `16³` section.** Every cell of a column is either real (the player can see it) or wholly `hidden_fill` (stone — ores, cave air, water, lava and all), on every send (first burst, streaming, reveal re-send). A partly-visible section therefore keeps its visible cells real and its hidden cells stone, so the ores behind the wall of a surface or cave-mouth section do not reach the client. `engine` mode remains the cheapest option when only fully-enclosed ores need hiding. See [design/visibility-culling.md](design/visibility-culling.md#granularity-the-4%c3%974%c3%972-avx-cell-ax3).
    - **Cell visibility is strict; the margin seeds candidates, not visible cells.** A hidden cell is replaced entirely with `hidden_fill`, never block-by-block. The margin seeds every section within `margin_blocks` as a candidate, but a sealed section — and a sealed cell within a visible section — is never sent real; only the section the player stands in may be sent sealed. The section graph and its per-cell visible mask are computed once per section and cached under the same global edit epoch, so a re-run after a section-border crossing does not recompute the whole view, and there is no global per-cell search (a full one at a correct radius measured ~3.5 s and stalled the tick).
    - **A fully-flooded void a player can see into is visible.** Culling treats water as see-through-but-not-passable: a pool the player looks at cannot reveal the flooded caves it drains into (the bug that let a player over water see cave systems), and a fully-clear (all-air or all-water) chain stays visible so an ocean is not turned to stone. But a *section with no opaque block at all* beyond a visible water surface is sent real, so a flooded cavern that is itself entirely water and connected by entirely-water sections is not hidden. It holds no ore, so the leak is cosmetic.
    - **Engine mode only hides ores whose six neighbours are all opaque, so any ore touching open air — cave faces, mineshaft gaps, a voxel that generation left exposed — is sent as itself.** That is the design's rule (the ore cannot be seen without removing a block only when it is fully enclosed), and it is the price of engine mode being cheap; `culling` mode hides the whole cell instead, cave walls included. The blind spot is deliberately loud here: x-ray on an ore floating in a cave still works, which is the common case in heavily-caved terrain.
    - **Light in a hidden cell is the stone's light** (block 0, sky 0), not the real block's. Every codec hands the same `BlockSource` to the block pass and the light pass, so masking one masks the other; for the common hidden cell — solid rock — those are the same value, and a sealed but lit pocket differs only until the column is re-sent on reveal. Keeping the real light needs the codec to read a second source, which is codec-side work and is deferred while the codec queues are owned by other tasks.
    - **Engine mode's reveal is per changed block, at the enclosing neighbour only, and deduplicated.** Breaking a block re-sends the ore next to it; a change further than one cell away does not, which is correct because enclosure only depends on the six touching cells. Each client remembers the cells it has already been sent real (`State::revealed`), so a neighbour change does not re-send the same ore; the memory is dropped when the column unloads or on respawn. A hidden block is never re-hidden once it has been revealed — the player already saw it, so there is no leak, but its blocks are back on the client until the column is next streamed.
    - **Cell re-hiding is likewise not done** in `culling` mode: a cell that becomes hidden after being revealed stays real until the column is next streamed (no leak, same reasoning).
    - **Engine mode substitutes whole block states, so it is codec-agnostic; the `culling` fallback for a version with no chunk writer was never needed.** `hidden_fill = "air"` still falls back to stone for a survival player (the design reserves air for spectators/flying), and both modes apply to every game mode. The admin bypass is **explicit only**: `/visibility off` (or `/spectate xray off` while spectating), the `aether.antixray.bypass` node granted through `[permissions] grants` (the CMD-01 store fronts it now), and the `[anti_xray] bypass_players` list. **Operators are not bypassed automatically**, so an operator can watch the protection work and turn it off deliberately; `/visibility status` reports the state for the player; `worlds` is the per-world toggle. The startup log prints an `anti-xray :` line with the live mode, worlds and bypass list. Column-send overhead in engine mode measured ≈ 10 % on a quiet machine (`benches/anti_xray.rs`, target < 15 %), load-dependent because the build/runtime host is shared.

17. **Online / hybrid authentication is new and only partially verified.** The `[auth]` module implements Mojang's encryption handshake (server RSA-1024 keypair, AES/CFB8, the signed server-id SHA-1), the `hasJoined` and profile-API calls (`reqwest` over rustls, no OpenSSL), the durable premium-name lock store and the hybrid decision table, all covered by unit tests with a mocked API and a local mock HTTP server. **Hybrid keeps offline play open to everyone**: only a name that has *completed online auth on this server* is locked, and only a locked name is ever refused for auth reasons. An unlocked name that Mojang reports as premium is merely *offered* encryption — if `hasJoined` fails the client joins offline in the same (already-encrypted) connection, and if it drops mid-handshake the next attempt from the same address and name for 5 minutes skips the offer (`auth::bounce`). No live premium client was available, so:
    - **The `should_authenticate` field is gated by protocol id (`>= 766`, i.e. 1.20.5+), and sent `true`.** It was added in 1.20.5, not 1.19; an earlier version of this code had the gate inverted, which made a real 1.21.11 client read one byte past the Encryption Request, reject it and disconnect — logged as "dropped during online auth". The exact layouts are pinned by a test against the PrismarineJS `minecraft-data` field lists, and the full handshake was validated end to end against an independent Node client (Node's own `crypto`). The `1.19`/`1.19.2` Encryption Response carries a `has_verify_token` boolean between the shared secret and the token; a client that answers in the salt/signature form is refused rather than misparsed.
    - The "dropped during auth" memory is keyed by `(address, name)` only; behind a shared/NAT address or a proxy a legitimate premium client could, in principle, inherit a bounce left by someone else using the same name from the same address. It is a 5-minute, best-effort availability rule, not a security boundary.
    - Usernames must match vanilla's `[A-Za-z0-9_]{3,16}`; anything else is refused, which rules out padded, zero-width and homoglyph claims that would render as a near-copy of a locked name.
    - A corrupt premium lock **fails closed**: an unreadable lock key refuses the login (loudly logged) rather than silently admitting the name offline.
    - A per-address login rate limit (`login_rate_per_min`, default 10/min, `0` disables) caps how fast attempts can drive Mojang calls or park connection threads; it is a coarse sliding window, not a token bucket.
    - Skin/cape properties are forwarded to the **modern** Player Info packet (1.21.11/26.x) only; the older codecs still send an empty property list, so a premium skin renders as the default there.
    - Operator and whitelist entries still name a player (`name` or `name@address`); they cannot name a uuid yet.
    - Offline uuids remain this engine's FNV derivation (`aether_api::player::offline_uuid`), not vanilla's MD5 `OfflinePlayer:<name>`; that is pre-existing and unchanged here, and it means a world keyed by the engine's offline uuid does not match one keyed by a vanilla offline server's.
    - `/aether auth migrate <name>` moves the saved player-state and inventory blobs from a name's offline uuid to its locked premium uuid (never overwriting existing premium data); it does not move position-keyed block containers, chests or the journal.
    - `cargo deny` ignores `RUSTSEC-2023-0071` (the `rsa` crate's unpatched Marvin timing side channel) — the standard login exposure every RustCrypto-based server has; a dependency swap would mean OpenSSL, which the task forbids.
18. **The WebAssembly plugin system is at its first stage (P1).** `crates/aether-plugin` is a Wasmtime 36.0.18 component-model host behind the server's `plugins` feature (on by default): it loads `plugin.toml` manifests, runs `wasm32-wasip2` components under per-call epoch interruption, a shared per-tick budget, a per-plugin memory cap, an init fuel budget and a fault counter, and runs the `before-*` / `after-*` / `on-tick` / `on-command` event bus wired at the game's hook points; `plugins/examples/hello` is the reference. Capabilities are deny-by-default (the operator must grant each), plugin commands cannot shadow a built-in, duplicate ids are refused, and a plugin may declare `deny_on_fault` to fail closed on a `before-*`. Four gaps are known:
    - **WASI is linked but granted nothing.** A Rust `wasm32-wasip2` component imports the WASI 0.2 surface for its standard library, so the host links `wasmtime-wasi` to satisfy the imports. The context is `WasiCtxBuilder::new()` — no preopens, no environment, no arguments, closed stdin, sink stdout/stderr and every network address denied — so a plugin has no way out of the sandbox, but "no WASI at all" is not yet true.
    - **`after-enchant` has no server hook point.** The event is in the WIT package and the host, but enchantment behaviour is not implemented, so nothing calls it; the E1/E2 work will.
    - **Economy and registries are not plugins yet.** P2 (the economy service and `storage.ledger`) and P3 (plugin-registered custom enchantments/items) are not implemented: the economy still runs the built-in PostgreSQL `Economy`, and the frozen `aether:plugin@0.1.0` world means they will arrive as a new package version.
    - **No native tier and no hot reload.** The native C-ABI tier and hot reload from the design are not started.

19. **The plugin SDK is a native service plugin with partial coverage (PS1).** The SDK ships as a native plugin (`plugins/sdk`, tier `native`) that publishes `sdk.permissions@0.1`, `sdk.commands@0.1`, `sdk.messages@0.1`, `sdk.players@0.1`, `sdk.scheduler@0.1`, `sdk.cooldowns@0.1` and `sdk.confirm@0.1`; a dependent (native or WASM) declares them in `plugin.toml` `requires` and calls them, and the host refuses the load with a clear error when the SDK is disabled. The command builder registers through the **core command registry** (`commands::registry::register_plugin`), so its commands are dispatched and permission-checked by the core gate (a core name is refused). Known limits:
    - **Permissions are read-only and fail closed.** The core permission model (CMD-01) is fronted: `sdk.permissions` `check`/`require`/`level`/`groups` resolve through the host backend to the core store, and a host without a core answers deny/zero/empty rather than guessing. The per-player **write** model (CMD-02) is absent, so `grant`/`revoke` refuse — after the `permissions.admin` capability gate — instead of pretending the write happened. It is a facade, not a second implementation.
    - **Players give is unavailable; teleport and permission meta now work.** `players.teleport` is fronted by the core CMD-31 teleport service (see item 27), capability-gated on `players.teleport`, and returns `Err` only when the player is offline, the destination refuses entry, or no safe spot is found. `permission_meta` fronts the core store (CMD-02). `give` needs CMD-32, so it still returns the neutral answer (unchanged count) rather than guessing.
    - **Config is host-backed, not a registry service.** `sdk.config` reads the caller's `[plugins.<id>]` values directly in the host bridge, so it works whenever the host does and `revision()` is constant until a config-reload counter exists.
    - **Timers are polled, not called back.** The frozen `aether:plugin@0.1.0` world has no callback export, so `sdk.scheduler` records due timers and the dependent polls `poll()` on its own `on-tick`; the SDK cannot invoke a WASM dependent's closure.
    - **A dependent generates its own bindings.** `wit-bindgen` 0.57 cannot export a world from a separate bindings crate, so `crates/aether-plugin-sdk` ships the `dependent` world and the `requires!` macro, and a dependent runs `generate!` in-crate (see `plugins/examples/greet`). The prelude re-exports the generated service modules; there are no typed `permissions()`/`commands()` resource handles, because the WIT is stateless.
    - **`requires!` is unenforced.** The macro emits a `REQUIRES` constant that nothing reads; the host reads the dependency from `plugin.toml`, so the two are kept in step by the author.
    - **The capability gate is in the service layer.** `plugins/sdk` checks `permissions.admin` on grant/revoke and `messages.send`/`messages.broadcast` on sends, reading the host's record of the caller's effective grant by caller id. Native dependents are trusted-by-install, so the gate is a consistency check for them, not a sandbox.
20. **The admin web interface (WEB1 + WEB2) is a native plugin over one embedded HTTP server.** `plugins/webadmin` serves, all read-only and from one `std::net` server with plain HTML+small JS (no framework, no CDN): a live-ops dashboard (TPS/MSPT/memory/players), the heaviest regions (a sampled per-region tick-cost ranking plus a heat grid), a players list with live/saved inventories and per-player profiles; a top-down map (top block per column, cached, re-rendered on a block change) with a live player/entity overlay; and a journal "time slider" (per-block history, an area's changes over a window, and tiles *as they were*). Its data comes from two seams: the server attaches the live `World` in `install_native` (map + history) and publishes the `ops@0.1` service (`crates/aether-server/src/web.rs`, trait in `crates/aether-ops`) the plugin resolves for the dashboard/regions/players/overlay and player names. Covered by unit and end-to-end tests. Known limits:
    - **Regions are sampled, not profiled.** A background thread (not the tick thread) rebuilds the table once a second from no-copy snapshots and decays it; a spike between samples is not attributed. `redstone_updates` is always zero until the redstone engine is wired (it is a standalone crate today), and `chunk_sends` counts the join burst and streamer per region since the last sample, not every packet.
    - **The profile store is the only record of first/last seen and playtime.** Nothing else in the engine persists them; `WB` + uuid in the world KV is written on join and leave, so a player who has never joined since this stage has no row.
    - **No ender chest.** The inventory view has the field, the engine has no ender chest.
    - **Login is a token, not accounts.** A static `[plugins.webadmin] token` or a five-minute one-time `/webadmin token` (operator level 3), carried as an `HttpOnly` cookie or `?token=` (a query token on a page is upgraded to the cookie). No users, roles or sessions beyond that; loopback HTTP, no TLS, no keep-alive; plugins must be enabled (`[plugins] dir` set), like any plugin. The socket layer is hardened against one client (global and per-IP connection caps, a bounded worker pool, request-line/header/body size caps, an absolute per-request deadline, and a rate limit over the tile/history endpoints) but is still not built for public traffic.
    - **It reads the journal directly, not through PA2's service.** The time machine and the history pages go through the plugin's own type-erased `HistorySource` (`column_events`, `for_each_event`, `for_each_actor_event`); PA2 now ships the paged, capability-gated `sdk.history@0.1` service, and this trait is the seam that should move onto it.
    - **The area/time listing scans the overlapped chunk columns** rather than a dedicated spatial index; a single block's history is an indexed column scan, but a large radius reads each touched column whole (clamped to a fixed radius/result/scan budget). Tile invalidation rides the `before-block-place`/`after-block-break` events, so a plugin or fluid write does not drop a cached tile.
    - **The map palette is the offline `vanilla_map` palette**, fixed per block name, not vanilla grass/foliage tinting; a modded block gets a hash-derived colour. Water is tinted by depth, not by biome.
21. **The permission core is the level/node model, groups, inheritance, per-world context and meta; `/lp` is next.** `crates/aether-server/src/permissions.rs` (CMD-01 + CMD-02) holds the vanilla op levels `0..=4`, a lower-case dot-separated node model with a per-node default of allow/deny/op, the subject-aware resolver (`check_for`/`check_in`) the command registry, the plugin commands and the SDK's `permissions` service call, and the built-in `op` group (level 4). A **group** now carries a parent set, a `priority`, explicit nodes and prefix/suffix/weight meta; a **player** carries explicit nodes and meta. A check resolves the player's nodes, then every reachable group ordered `(priority desc, depth asc, id asc)` (child before parent), then the declared default; an explicit grant/deny never lowers a command's op floor. A node may carry a **context** (a dimension/world key): a matching context-specific node beats that holder's global one and a mismatched context is skipped. `config.operators` is only a **seed** for the `op` group: the store is persisted to `<world_dir>/permissions.toml` (atomic temp-file + rename; format in [design/permissions.md](design/permissions.md)), loaded before seeding, merged add-only, so an entry already in the store is not duplicated and removing a name from the config does **not** silently deop — deoping is an explicit action (CMD-08). An inheritance cycle is rejected at load. A hand-edited or corrupt file cannot weaken the built-in `op` group (level 4, non-deletable). Unknown nodes fail closed. Writes clone the store off the tick and swap an immutable `Arc` snapshot, so a reader never sees a half-applied edit and the hot path takes no `Mutex`. The SDK's `grant`/`revoke`/`meta` are wired to the write model. What is not here yet: **`/op`/`/deop`** (CMD-08) so `op` membership is config-seeded or plugin-written only; the **LuckPerms-style management UI / `lp` command / web editor and tracks** are CMD-33; and **temporary nodes** (expiry) are not modelled yet. The store is implemented in-process in the core rather than as a native plugin as the brief's CMD0 review suggested — see item 26.


22. **The sidebar scoreboard is a native plugin over a core packet path (SB1), and placeholders are a shared SDK service.** `plugins/sidebar` composes a per-player panel from `config.toml` layouts and hands it to `PlayerHandle::update_sidebar`, which renders 1.8 through 26.x (teams up to 1.20.2; the score's display name plus `number_format = blank` from 1.20.3) and resends only changed lines; the tab-list header/footer and a `sidebar@0.1` service (line overrides, toggle) ride along (see [design/sidebar.md](design/sidebar.md)). The `%placeholders%` are a separate shared service, `sdk.placeholders@0.1`, so menus and chat read the same registry ([design/plugin-sdk.md §7.9](design/plugin-sdk.md)). The limits:
    - **CMD-15 is not landed.** The core keeps only the sidebar model and packets, not the full vanilla `/scoreboard` model, commands and storage (CMD-15a/b). `mode = "yield"` is **wired** (the plugin hides its panel while `HostBackend::vanilla_sidebar_claimed` reports the vanilla model owns the slot), but the core always answers `false` until CMD-15 lands, so it has no visible effect yet; `override` is the default.
    - **`%level%` is 0, `%world%` is the overworld, `%displayname%` is the login.** The experience level is not routed into `PlayerExtra`, no per-player dimension is plumbed through, and nicks are not stored. `%ping%` (keep-alive round trip), `%tps%` (smoothed measured tick rate), `%time%`/`%world_time%` (world clock) and `%server_time%` (server wall clock) are real; there is no per-plugin clock switch (the sidebar's `clock` config was dropped when the registry became shared).
    - **A WASM placeholder is pushed, not called back, and a name is owned.** `aether:sdk/placeholders@0.1` is an import interface (adding an import refuses nobody); a native provider hands over a closure, a WASM one declares a name and pushes a value per player because a component cannot hand the host a closure and the frozen `aether:plugin@0.1.0` world has no placeholder callback export. A custom name is **owned by its first registrant** — a second caller's register/set is refused and logged, so an untrusted WASM plugin cannot spoof another's `%name%` — and the built-ins are reserved from the pushed path (a native closure may still shadow one). Pushed values and new providers bypass the resolved-token cache; native closures are cached per player per token for `placeholder_cache_ticks` (default 20).
    - **Every scoreboard/tab id and team layout is pinned against `minecraft-data`** (and, for 26.x, each release's own data-generator `packets.json`): the 1.8 team packet's `displayName`, the 1.13–1.20.2 JSON team name, the 1.21.5 VarInt-enum visibility/collision form (`NbtEnums`), the 1.21.6 flags form, the tab-list ids (760 `0x63`, 766/767 `0x6d`), and the 26.x ids (775/776 +2, 777 +4 objective/score/display/team, `reset_score` +3 at `0x50`).

23. **Staff vanish + admin spectate is a native plugin over core hooks (SP1).** `plugins/staff` drives `/vanish`, `/spectate` and `/spectate xray` through `HostBackend::staff_*`; the core (`crates/aether-server/src/staff.rs`) holds the per-player flags, the visibility predicate, the spectate snapshot and the anti-xray override. See [design/staff.md](design/staff.md). Known limits:
    - **No camera attach.** There is no Set Camera packet in the protocol layer, so `/spectate <player>` teleports the spectator onto the target's position instead of riding their eyes. The state save/restore (location, mode, inventory, health/hunger/effects/flight) is exact.
    - **A few vanish side-effects are not wired because the core feature does not exist yet.** `/list` is still a CMD-09 stub, the command tree is static (no dynamic name completion), there is no server-list player count/sample, and beds do not run a sleep count — so a vanished player is absent from them by construction. Each must call `staff::visible_to` when built. The paths that do exist are wired: the tab list, entity tracking (despawn and spawn), join/quit messages, and mob targeting/spawning (the entity tick marks a vanished player non-huntable and drops them as a spawn anchor). The movement/teleport/sound broadcasts are not filtered — the client ignores packets for an entity it does not hold.
    - **The vanish flag is separate from item pickup.** The entity tick gives a vanished player `huntable = false` (no mob targets them) but keeps `survival = true`, so they still collect drops and arrows. Item pickup and arrow hit both read these fields, not `huntable` directly.
    - **The command gate is the CMD-01 permission core; `vanish.see` is not consulted.** `/vanish` and `/spectate` are registered through the core registry with op level 0 and the `aether.staff.*` nodes, so CMD-01's gate (`permitted`) resolves them (a node left undeclared defaults to `op`, i.e. level ≥ 1). The plugin body still checks the player's operator level for its own replies, and who may see the vanished is the operator flag — the `aether.staff.vanish.see` node is declared but not resolved, because a native plugin has no per-node check hook yet.
    - **Relog persistence re-applies before the join burst.** `after-player-join` runs before the tab entries, spawns and join message, so a returning vanished player is neither spawned to others nor announced — there is no window. `[plugins.staff] persist = false` drops a vanish on logout instead.
    - **`/spectate` is the Aether admin command, not vanilla's.** It is not in the core stub registry; it carries `aether.staff.spectate` and the per-admin anti-xray control, which vanilla's entity-following `/spectate` has no equivalent of.

24. **Menus are a native plugin with a core virtual-window API (MN1).** The shared chest-menu host ships as a native plugin (`plugins/menus`, tier `native`) that both **exports** the `aether:menus@0.1` service — callable by native and WASM dependents, one call to open a menu — and **loads** declarative `plugins/menus/menus/*.toml` files (title, layout, items, view/click conditions, ordered `[command]`/`[console]`/`[message]`/`[open]`/`[close]`/`[give]`/`[back]` actions), registering each file's `open_commands` with the core command registry (so `/shop` is permission-checked like any command) plus `/menu <name>` and an op-gated `/menus reload`. The core gains a **virtual menu window** (`WindowKind::Menu` / `MenuShape`): the slots are stand-ins, and the core intercepts **every** click — left, right, shift, number-key swap, offhand, drop, drag, double-click collect, creative middle-click — hands it to the plugin and resyncs the client, so no click can move a stack into or out of the player's real inventory (property-tested over random click sequences). Known limits:
    - **Only the generic container shapes.** A menu is a chest of 1–6 nine-wide rows (`generic_9x1`…`generic_9x6`), a dispenser (3×3) or a hopper (5 slots); anvil, beacon and brewing menus are not offered.
    - **Name, lore, glint and model id render per version.** On 1.20.5+ a menu item's `name`/`lore` are the `custom_name`/`lore` components, `glint` is `enchantment_glint_override` (a bool) and `model` is `custom_model_data` (a VarInt before 1.21.4, the four-list record from 1.21.4 — an int maps onto a one-element `floats` list). Before 1.20.5 they are the NBT `display` tag, a hidden placeholder `Enchantments` entry with `HideFlags`, and the `CustomModelData` tag. `enchantment_glint_override` and `custom_model_data` have no codec on the pre-1.20.5 NBT slot, which is why glint there is a real (hidden) enchantment rather than an override.
    - **Economy conditions/actions are inert.** `balance>=` and `[economy] take` fail closed (the economy is not yet a service). `[give]` and `[sound]` work through the core (`give_or_drop`, the sound event); a sound name the client does not know is silently ignored by the client, and `[give]` overflow drops at the player's feet as `/give` does.
    - **Rate limit and coalesced resync.** A player may process at most 8 menu clicks per tick; the rest are dropped. Menu resyncs are coalesced to one full-window send per tick, not one per click (see `game::window`).
    - **`/menus reload` reads off the tick thread.** Files are read on a worker thread and installed on the next tick; the example `shop.toml` carries no `permission` so it opens out of the box (a declared permission would deny while the core permission model is unlanded).
    - **Placeholders are `%player%` only; the shared registry is not wired yet.** SB1 lands a shared `sdk.placeholders@0.1` registry (see §22), but menus do not yet resolve through it. `Menus::expand` is the documented hook that will call it; until then menus expand built-ins only and leave an unknown placeholder verbatim rather than blanking it. No local placeholder engine is grown.
    - **No menus on pre-1.20.2 codecs.** Protocols ≤763 (1.8.9–1.20.1) have no server-driven window support, the same limit as the recovery stash, so a menu does not open there.
    - **No live harness run.** The V1/MCC end-to-end (a bot opens a menu and clicks it) has not been run; the guarantee is covered by unit and property tests against the core router and the menus plugin.
25. **Voice chat is a native plugin for Simple Voice Chat and Plasmo Voice (VC1).** `plugins/voice` reimplements both server sides in-process: two UDP servers (default `:24454` / `:60606`), the plugin-channel handshakes, `AES-GCM` (SVC) and `AES-CBC/PKCS5` (PV) crypto (both checked against NIST vectors), one internal `VoiceFrame`, proximity/group routing, `/voice` admin commands and Ogg/Opus recording. The protocols are pinned against the mods' source (SVC branch `1.21.11`, compatibility version 18; PV channel `plasmo:voice/v2`), and cross-protocol audio is re-wrapped, not re-encoded. **The two UDP listeners are opt-in** — `[plugins.voice] svc_enabled`/`pv_enabled` default to `false`, so installing the plugin opens no port; set the one(s) you run. The server drives the keepalives both mods need (SVC `KeepAlive`, PV `Ping`), sends PV's `PlayerInfoRequest` on join with a retry schedule, and answers `SourceInfoRequestPacket` with a `SourceInfoPacket`. The known gaps:
    - **Transport covers protocols 764–775.** The core gained `ClientEvent::PluginMessage` / `ServerEvent::PluginMessage` and a `custom_payload` packet id per release; it is wired for 1.20.2 through 26.1 (764–775). **26.2 and 26.3 are `-1`** — their custom-payload id is not in the pinned `minecraft-data` (3.117.0) and is not guessed, so voice does not connect on those two releases yet.
    - **PV end-to-end encryption and RSA key exchange are not implemented.** PV's `ConfigPacket` can carry an RSA-encrypted AES key; this server sends the config without it, so PV audio is forwarded exactly as the client sent it. An SVC↔PV bridge therefore forwards opaque PV audio rather than decrypting it (which the server's own AES key would allow once RSA is added). The `pv_aes_key` config key was removed rather than left as a trap.
    - **SVC groups are in memory and non-persistent.** `add_group`/`remove_group`/`joined_group` and group audio routing work, but a group dies with the process and there is no password `GROUP_REGEX` validation or `MAX_GROUP_NAME_LENGTH` enforcement beyond the 24-char read bound. Group audio is forwarded as an SVC `GroupSound` (not distance-attenuated) to SVC members and as PV `SourceAudio` to PV members.
    - **No per-frame sequence replay protection or jitter buffer.** Frames are relayed as they arrive; the mods' TTL/reordering buffers are not reproduced. Per-sender token buckets and a capped inbound queue bound a flood, though.
    - **Opus is passed through, not negotiated.** Both mods send Opus, so no transcode is needed; SVC's `codec` is advertised as `VOIP` and PV's as `opus`, and an `OpusHead` with 48 kHz mono is used for recordings. A client that negotiated a different sample rate is not re-framed.
    - **Recording runs on its own thread.** Frames are handed to a writer thread over a bounded channel, so `/voice record` and Ogg writes never touch the tick; retention is a periodic walk on a second thread. A full writer queue drops frames (never blocks the game).
    - **`/voice spy` delivers a copy of matching frames to the admin's own voice client.** It needs the admin to have SVC/PV connected; it does not open a side channel.
26. **The permission store is core, not the native plugin the CMD-02 review sketched.** The CMD0 review of CMD-02 called for the store and its resolution to be a **native plugin** (`needs: oc/CMD-00N`), with the core keeping only the check API. It is instead implemented in `crates/aether-server/src/permissions.rs`, because the core check is on the hot path for every command, the block-break/place gates, `is_operator` and the SDK's `permissions` service, and the native loader gives a native plugin no way to answer the core's synchronous per-check call yet (a native plugin has no per-node check hook — the same limit noted for `aether.staff.vanish.see`). Moving it behind a service is therefore deferred until that hook exists; the model, file format and tests are written so the move is mechanical once it does. The `op` group, the persisted `<world_dir>/permissions.toml` and the fail-closed defaults are unchanged by the deferred move.
27. **The stats plugin reports only what the journal can derive (CMD-47).** `plugins/stats` (WASM) answers `/stats`, `/leaderboard` (`/lb`) and `/playtime` from cached aggregates: it folds `block_set` events into per-player counters on a scheduled timer (P1) and reads each player through the PA2 actor index, only since the last watermark, so no request scans the journal. **Distance, deaths and kills are always `0`** — movement, damage and death are not journalled, so the engine cannot derive them; the model keeps the fields so a later task that journals them fills them in without changing the command surface. Playtime is the plugin's own record, in world ticks, checkpointed to its KV on join/leave and on the refresh timer, so it survives a restart and a crash loses at most the ticks since the last checkpoint. Records are keyed by UUID with a name index, so a rename (CMD-38) maps to the same record. Unknown names and empty leaderboards answer `0`/"no data", never an error.

27. **The core teleport service is single-world (CMD-31).** `crates/aether-server/src/teleport.rs` is the service the built-in `/tp`/`/spawn`, the staff spectate move and the SDK `players.teleport` now go through: exact moves, a deterministic safe-spot search (`find_safe_spot`) and a bounded random one (`random_safe_spot`), reading `aether-physics` collision shapes and rejecting lava/fire/cactus/campfire. The plugin `players.teleport` path is capability-gated on `players.teleport` and resolves a safe spot host-side (the design contract, `docs/design/plugin-sdk.md` §7.4), so a plugin cannot drop a player into lava or the void. Known limits, all waiting on infrastructure that does not exist yet:
    - **No cross-world / cross-dimension move.** The engine runs one world per process and has no world registry or dimension-change codec dance, so every move is intra-world and `TeleportCause::Portal` is only a label (no portal block drives it). The cause enum is the seam the codec work will hang from.
    - **No vehicles, mounts or passengers.** There is no entity-vehicle model, so a teleport moves only the player; carrying/dismounting a vehicle and moving passengers together are not implemented.
    - **The hook seam is defined but not wired in production.** `TeleportHooks::allow_entry` (the region `entry` check) and `TeleportHooks::after_teleport` (the plugin observer) exist and are exercised by unit tests, but every production caller — the commands and the SDK path — goes through `teleport()`/`NoHooks`. The region spatial index has landed (CMD-29a, `region.rs`), but the protection check and its hook wiring are CMD-29b and are not; the frozen `aether:plugin@0.1.0` event world has no `after-teleport` export (`tests/wit_world.rs` forbids adding one without a package bump), so no region veto or plugin event fires today; the seam is the extension point those two will use.
    - **Chunk loading is per-read, not batched per tick.** A search far from spawn materialises columns through the world's ordinary `ensure_column`, so the cost of a distant `/rtp` is bounded by the search radius rather than by a per-tick load budget.

### B. Known Deviations Registry (Phase 1 — accepted on purpose)
These are **not bugs** in Phase 1 — they are documented, temporary compatibility gaps that must be recorded in the engine config and closed in Phase 2.

| Subsystem | Phase 1 deviation | Phase 2 target |
|-----------|-------------------|----------------|
| **Redstone** | Quasi-Connectivity (QC) ignored across inactive chunk borders | Full dependency graph with cross-chunk QC |
| **Fluids** | Scheduled-update flow with vanilla delays and levels on one queue, capped per tick; the `getFlow` vector pushes entities and items, waterlogged blocks are sources, and loaded generated fluid that can flow is woken (all bounded) | Deterministic fluid layers 1:1 with Vanilla |
| **Scheduled block ticks** | Falling blocks, crop growth and leaf decay on one scheduler plus a random-tick pass; pending ticks are written per chunk (`BT`/`BF` blobs, reloaded as the chunk loads) and **survive a restart**, but light is assumed full-bright and block tags are name lists | Real light and tag data |
| **Update order** | Simultaneous redstone updates ordered by the parallel graph | Strict deterministic directional-priority queue |
| **Entity spawn** | Batched async spawn every N ticks (every 40 ticks, per-player caps, sky/darkness test without light levels) | Per-tick precise spawner |
| **Mob AI** | Cached A\* over the block grid with a per-tick node budget and straight-line fallback; no doors, no spider climbing, no jumping gaps | Flow-Field navigation |
| **Lighting** | Real block/sky light by mask dilation, but recomputed per chunk send and per column only: no incremental relight on a block change, no cross-column propagation, no caching. The demo and the 1.8.9 codec still read `FullBright` | Incremental relight off journal events, cross-column propagation, caching |

### C. Engineering risks & trade-offs
- **RAM overhead: +15–25%.** SoA masks, Morton order, and redstone graphs cost more memory than classic structures. Accepted for cache-locality and SIMD wins.
- **x86-64 first.** The first version targets x86-64 with AVX2; other ISAs are deferred. Users on ARM/RISC-V are unsupported until later.
- **Determinism vs. parallelism.** Aggressive parallelism increases the risk of non-deterministic results if Safe-Point merges are wrong — needs strong test coverage.
- **Compatibility ceiling in Phase 1.** 70–75% Vanilla compliance means some contraptions (QC-dependent redstone, tick-perfect fluids) will behave differently until Phase 2.
- **External dependency choices.** Fjall was chosen over RocksDB for the KV store (it is what the engine uses); Elixir/OTP vs. C++/Rust for the Gateway is not finalized, and a wrong pick is expensive to reverse.

### D. How to report a problem
Open a GitHub issue with: the subsystem, whether it's a **bug** or an **accepted deviation** (check the table above first), reproduction steps, and — for performance issues — a Tracy capture or the relevant benchmark scenario. See [CONTRIBUTING.md](../CONTRIBUTING.md).
